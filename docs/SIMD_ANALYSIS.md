# SIMD opportunities in the log-parsing hot path

Where data-parallel byte scanning can speed up `pg-plansight-core`, which
candidates actually pay, and which do not. Every number below is measured, not
estimated.

Reproduce with:

```bash
cargo bench -p pg-plansight-core --bench simd_candidates
```

## 1. Where the time actually goes

A callgrind profile of an end-to-end parse (`cargo run --release -p
pg-plansight-core --example profile_parse 1500`, then
`valgrind --tool=callgrind`) attributes the run as:

| Cost centre | Share of instructions |
| --- | --- |
| `regex_automata` bounded backtracker | 27.8% |
| `regex_automata` lazy DFA (fwd + rev) | 8.0% |
| malloc / free / memcpy / memset | ~14% |
| `str::trim_matches` | 2.8% |
| everything else | remainder |

The backtracker is the engine `regex` falls back to for **capture extraction**
on short haystacks, and the parser calls `captures()` several times per plan
line. Measured per call on a representative node line:

| Pattern | ns/call |
| --- | --- |
| `LOG_LINE_PATTERN` (timestamp split) | 1177 |
| `COST_REGEX` (`(cost=..)` tuple) | 931 |
| `INDEX_REGEX` | 808 |
| `TABLE_REGEX` | 558 |

This matters for framing: **the workload is regex- and allocation-bound, not
byte-scan-bound.** It is not a case of "a scalar loop is scanning bytes one at
a time and SIMD would scan 32". The opportunity is that each of those patterns
describes a *fixed byte shape* — a timestamp, a cost tuple, a whitespace run —
which can be recognised by vector compares instead of by a regex engine.

## 2. Separating the two effects

Replacing a regex with a byte scanner bundles two distinct wins:

1. **Algorithmic** — not running a regex engine at all.
2. **Vectorisation** — comparing 16 or 32 bytes per instruction.

Only the second is attributable to SIMD, and on data this short it is the
smaller of the two. So `crates/core/src/simd_scan.rs` implements **both** a
`_scalar` and a `_simd` version of every scanner, and the benchmark measures
three tiers — `current` / `scalar` / `simd` — on identical input. Reporting a
single "15x SIMD speedup" would be misleading; the split below is the honest
accounting.

## 3. Results

4-vCPU Cascade Lake (AVX2 + AVX-512), 2,000-plan synthetic auto_explain log
(~3.25 MB, ~89% continuation lines) generated by the same generator as
`benches/log_parsing.rs`.

**On absolute numbers:** this shared VM drifts. The same unchanged binary
measured ~40% faster in a later session than an earlier one, far beyond the
±10% run-to-run variance seen *within* a session. Every table below is
therefore from a single session and internally consistent, and every claimed
delta is a paired criterion A/B measured minutes apart. Do not compare
absolute figures across sections that were captured at different times, and
treat sub-10% gaps (§3.2) as parity rather than signal.

### 3.1 Candidates that pay

| Site | Current | Scalar bytes | SIMD | Total | SIMD's own share |
| --- | --- | --- | --- | --- | --- |
| Timestamp split, realistic line mix | 886.3 µs | 97.0 µs | **75.4 µs** | **11.8x** | 1.29x |
| Timestamp split, timestamped lines only | 804.7 µs | 12.2 µs | **10.1 µs** | **79.5x** | 1.20x |
| Cost tuple extraction | 2874.6 µs | 472.1 µs | **336.2 µs** | **8.6x** | 1.40x |
| Indentation counting | 60.1 µs | 43.5 µs | **35.0 µs** | **1.7x** | 1.24x |

The `SIMD` column measures the *shipped* code path for the timestamp split and
indentation, i.e. the integrated functions from §5, not a bench-local copy.

Read the last two columns together. The timestamp split gets 11.8x overall but
only 1.29x of that is vectorisation — dropping the regex is what does the
work. Indentation is the opposite: it never used a regex (it decoded UTF-8
`char`s to count leading spaces), so proportionally more of its gain is SIMD.

### 3.2 Candidates that do not pay

| Site | Current | Best alternative tried | Verdict |
| --- | --- | --- | --- |
| Plan-node detection (`(cost=` present?) | 421.7 µs | 398.1 µs (`memchr::memmem` screen) | **Parity** |
| Node-type classification | **218.3 µs** | 483.6 µs (hand SIMD), 907.1 µs (aho-corasick) | **2.2x slower** |

Both negative results have the same cause, and it is worth stating plainly:
**this code is already SIMD-accelerated, just not by us.**

- Node detection runs `plan_regex.is_match`. The `regex` crate already applies
  a SIMD literal prefilter internally, so adding our own `(cost=` screen in
  front of it duplicates the scan. Even `memchr::memmem`, the best-in-class
  implementation, only reaches parity.
- Classification does `line.to_lowercase()` once and then up to eight
  `contains()` calls. `contains()` is `memchr::memmem` with a SIMD rare-byte
  prefilter, and it short-circuits on the first needle that hits. Replacing it
  with a per-needle case-insensitive vector search means eight passes instead
  of one prefiltered pass. Single-pass multi-pattern `aho-corasick` also loses,
  because preserving the existing needle-priority semantics requires
  overlapping iteration, which disables its Teddy prefilter.

The allocation `to_lowercase()` performs is still real malloc pressure, but the
fix for that is to hoist it, not to vectorise it.

### 3.3 Aggregate effect

Per-site numbers do not aggregate without knowing call counts, so the counts
were measured directly by instrumenting the parser with atomic counters over a
2,000-plan parse:

```
split_log_line       36,993   (once per line; only 4,000 reach the regex —
                               the leading-tab fast-reject handles the rest)
get_indent_level     51,986   (~1.6x per continuation line)
extract_cost         19,993   (once per node line)
COST_REGEX::is_match      0   (`parse_lines` is not on this path at all)
```

The `hot_loop_composite` benchmark replays exactly these three winning sites at
these frequencies (indentation at 1x rather than 1.6x, making it a conservative
floor), against the `end_to_end_anchor` full parse. Measured *before*
integration:

| | Time (2,000-plan log) |
| --- | --- |
| `hot_loop_composite/current` | 31.97 ms |
| `hot_loop_composite/optimised` | **4.79 ms** (6.7x) |
| `end_to_end_anchor/parse_2k_plans` | 130.25 ms |

The composite was **24.5%** of total parse time, and the change removed 27.2 ms
of it — a projected **~21% end-to-end reduction, about 1.26x**.

That projection is kept here as the prediction it was. The integration in §5
actually delivered **−29.5%**; §5 explains why the projection came in low.

## 4. What is in the tree

`crates/core/src/simd_scan.rs` — four scanners, each with a scalar and a
vectorised implementation and a runtime AVX2 check (SSE2 needs none; it is
baseline on x86_64). On non-x86 targets the `_simd` entry points alias the
scalar ones, so behaviour is identical everywhere.

Five scanners now, counting `parse_cost_tuple`. Three of them are on the
parser's hot path as of §5; `find_literal_*` and `find_ascii_ci_*` are not,
and remain as the evidence behind §3.2 and as primitives `parse_cost_tuple`
builds on.

Correctness is the reason to trust the numbers, so each scanner is required to
be *exactly* equivalent to what it shadows, including the corners:

- `\d` in the `regex` crate matches Unicode digits, not just `[0-9]`.
- `[A-Z]{2,5}` is greedy but fails the whole optional group below 2.
- `(?::?\d{2})?` backtracks the colon away when two digits do not follow.
- `char::is_whitespace` is true for non-ASCII code points such as U+00A0.
- Full Unicode lowercasing is not byte-wise (`'İ'` lowercases to two code
  points), and PostgreSQL identifiers may be non-ASCII.

Rather than reimplement those tables, a scanner returns `Verdict::Unsure` the
moment a non-ASCII byte could change the answer, and the caller defers to the
regex — so behaviour stays identical by construction. Real PostgreSQL
timestamps are ASCII, so this costs nothing in practice.

The unit tests assert equivalence differentially, including a 20,000-case
generated corpus for the timestamp scanner and a 30,000-case one for the cost
parser. The benchmark additionally gates every timing group behind a
full-corpus equivalence check, so a number can never come from a scanner that
silently does less work.

## 5. Integration — done, and re-measured

All three winning candidates are integrated. The two measured as losses were
left alone.

| Plan | Site | Status |
| --- | --- | --- |
| A | `parser_utils::split_log_line` | Integrated |
| B | `plan_parser::extract_cost` | Integrated |
| C | `parser_utils::get_indent_level`, `plan_parser::count_indentation` | Integrated |
| — | node detection, node classification | **Not changed** (measured as losses, §3.2) |

Each site tries the byte scanner and falls back to the existing regex or
`char` path when the scanner reports `Verdict::Unsure` — a non-ASCII byte
where the regex would consult Unicode tables. The fallback is the correctness
backstop, not an optimisation detail.

`extract_cost` goes further and declines (`None`) on anything that is not
*precisely* the `(cost=..)` shape, including a second `..` in the numeric run,
Unicode digits, vertical-tab separators, and PostgreSQL 18's fractional
`rows=`. A false negative costs only the regex call that would have happened
anyway; a false positive would silently report a different cost. See
`simd_scan::parse_cost_tuple`.

### End-to-end result

Measured on the 2,000-plan corpus, as paired criterion A/Bs against saved
baselines. **Absolute timings on this shared VM drift by up to 40% between
sessions, so all three states below were measured in one session** and only
the paired deltas are meaningful:

| State | Parse time | Allocations | Per plan |
| --- | --- | --- | --- |
| Original | 76.42 ms | 458,449 | 229.2 |
| + allocation fixes | 71.62 ms | 390,470 | 195.2 |
| + SIMD scanners | **47.94 ms** | **366,344** | **183.2** |

| Comparison | Delta | 95% CI | p |
| --- | --- | --- | --- |
| Allocation fixes alone | −6.3% | | |
| SIMD scanners on top | **−29.5%** | [−31.2%, −27.5%] | 0.00 |
| **Cumulative** | **−35.5%** | [−37.4%, −33.4%] | 0.00 |

**1.59x faster end-to-end**, and 20% fewer allocations per plan.

The SIMD result beat the projected ~21% (§3.3) for two reasons, both of which
made the projection conservative rather than the measurement generous:

1. The `hot_loop_composite` projection replayed indentation once per
   continuation line, but the parser really calls it ~1.6x that often.
2. Plan C also removed a `Vec<char>` allocation per plan line in
   `count_indentation` — visible above as the further 390,470 → 366,344 drop,
   which the timing-only projection did not model at all.

### Verification

The pre-existing differential tests for `split_log_line` — 50,000 fuzz cases
over an alphabet including Arabic-Indic and fullwidth digits, plus realistic
fixtures — pass unchanged against the scanner. (An earlier draft of this
document claimed that function had no direct tests; it did, and they are
better than what would have been added.) `parse_cost_tuple` gained three
differential tests including a 30,000-case generated corpus asserting it never
reports a tuple the regex would not.

The benchmark's `current` arms now hold local copies of the pre-integration
implementations. Calling the library functions would have silently turned the
comparison into scanner-versus-scanner once the integration landed; the arms
additionally assert that the shipped functions still agree with the legacy
ones over the whole corpus.

## 6. What is left

Node detection and node-type classification remain unchanged and should stay
that way — §3.2 measured both as losses against code that `regex` and
`memchr` already vectorise internally.

The remaining lever is not SIMD. `docs/ALLOCATION_ANALYSIS.md` covers
allocation churn, which is now 183 allocations per plan; the largest single
remaining source is the per-node property `HashMap<String, String>`.

Worth noting for anyone extending this: most of the win in Plans A and B came
from *removing the regex*, not from vectorising. The `scalar` tier in §3.1
captures 88% and 84% of those two wins respectively with no `unsafe` at all.
If the `unsafe` in `simd_scan` ever becomes a maintenance concern, dropping to
the scalar implementations would surrender only a small fraction of what was
gained.

## 7. Integration plans (as executed)

These are the plans the integration in §5 followed, kept for the rationale
and the risk notes. Each plan was independent and separately revertable. They share one rule: the
scanner never decides a case the regex would decide differently — on
`Verdict::Unsure` the caller falls back to the existing code, so the fallback
path is the correctness backstop rather than an optimisation detail.

Common prerequisites, done once:

- Promote `LOG_LINE_PATTERN` from `pub(crate)` to `pub` **or** keep benches
  using `RegexPatterns::default().log_line_regex` (what they do today). No
  library change is required for the plans below.
- Add a CI job running the `simd_scan` differential tests on a
  non-AVX2 runner, or set `-C target-feature=-avx2` in one matrix leg, so the
  scalar fallbacks stay exercised. Today they are only covered where the
  runtime detection happens to fail.

### Plan A — timestamp split (largest win: 14.3x on the site, ~9% end-to-end)

**Touches** `crates/core/src/parser_utils.rs::split_log_line` only. Every
caller (`log_parser`, the exporter's checkpoint scan, the pg extension's
ingest offset logic) goes through this one function, so nothing else changes.

1. Change the body to try `simd_scan::timestamp_prefix_len_simd` first:
   `Match(n)` → `Some((&line[..n], &line[n..]))`; `NoMatch` → `None`;
   `Unsure` → today's `fallback.captures(line)` path, unchanged.
2. Keep the existing leading-byte fast-reject in front of it. It costs one
   compare and already eliminates ~89% of lines, and the scanner's own length
   check does not subsume it.
3. Drop the `fallback: &Regex` parameter? **No** — keep it. It is what the
   `Unsure` arm needs, and removing it would force every caller to change.

*Verification*: `split_log_line` has no direct unit tests today; add one that
runs the generated corpus from `simd_scan::tests` through both
implementations. The bench's equivalence gate already does this over the
realistic corpus and must keep passing.

*Risk*: low. The function is small, single-purpose, and the fallback preserves
semantics for every input the fast path declines.

### Plan B — cost tuple extraction (7.6x on the site, ~11% end-to-end)

**Touches** `crates/core/src/plan_parser.rs::extract_cost`. This is the
larger end-to-end contributor despite the smaller ratio, because it runs
19,993 times per 2,000 plans against the timestamp split's 4,000 regex hits.

1. Move the byte parser currently prototyped in
   `benches/simd_candidates.rs::extract_cost_scanned` into `simd_scan` as a
   real function returning `Option<PlanCost>`.
2. In `extract_cost`, try it first and keep `COST_REGEX.captures` as the
   fallback for `None`, preserving the existing `ParseError::InvalidCostFormat`
   message on total failure.
3. Do **not** delete `COST_REGEX` — `parse_lines` still uses it for `is_match`,
   and §3.2 showed that site should be left alone.

*Verification*: the parser has extensive plan-parsing tests; they cover this
transitively. Add a direct differential test over the node lines of the bench
corpus, mirroring the bench's gate.

*Risk*: medium — this one parses numbers, so it has more corners than a shape
check (`rows=` with a decimal point on PG18, `cost=` with no fractional part).
The prototype already handles the `..` separator ambiguity; extend the
differential test to cover PG18's fractional `rows=` before merging.

### Plan C — indentation (2.4x on the site, ~0.2% end-to-end)

**Touches** `crates/core/src/parser_utils.rs::get_indent_level`, and
optionally the near-duplicate `PlanParser::count_indentation`.

1. Try `simd_scan::leading_whitespace_simd`; on `Unsure` fall back to today's
   `chars().take_while(char::is_whitespace).count()`.
2. `count_indentation` in `plan_parser.rs` does the same job via
   `line.chars().collect::<Vec<char>>()` — which allocates a `Vec<char>` per
   line. Fold it into `get_indent_level` while here; that also removes an
   allocation, so it belongs to both this plan and the allocation work.

*Verification*: covered by existing plan-structure tests, which are sensitive
to indentation (it drives the node tree). The `Unsure` fallback matters more
here than elsewhere: `char::is_whitespace` is true for non-ASCII code points,
so the byte scanner must decline rather than guess.

*Risk*: low in isolation, but note the payoff is small. Take it for the
allocation removal in step 2 as much as for the SIMD.

### Not planned — node detection and node classification

§3.2 measured both as losses (parity and 2.2x slower respectively). They are
already SIMD-backed inside `regex`/`memchr`. No work should be scheduled here;
the `find_literal_*` and `find_ascii_ci_*` scanners stay in `simd_scan` as the
evidence for that conclusion and as primitives Plan B builds on.

### Sequencing and expected total

Plans A and B are independent and together account for essentially all of the
projected ~21%. C adds ~0.2% and one allocation per plan line.

A reasonable order is **B, then A, then C** — B is the biggest end-to-end
contributor and the riskiest, so it benefits most from landing alone where a
regression is easy to attribute. Re-run
`cargo bench -p pg-plansight-core --bench simd_candidates` after each; the
`end_to_end_anchor` group is the number that matters, and CodSpeed already
tracks the core benches per-commit.
